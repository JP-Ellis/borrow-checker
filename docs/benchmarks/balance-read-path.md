# Balance read path — measured

Generated by `mise run bench:fixtures` followed by `mise run bench`
(`cargo bench -p bc-core`, criterion 0.8, sample size 10 per benchmark).
Fixtures were **regenerated from scratch for this run** by the current
generator, and every number below comes from that single run.

**Determinism, precisely.** The generator's *ledger shape* is deterministic
(seed 42): transaction count, dates, account assignment, elision, and skew
reproduce exactly across runs, and the regenerated fixtures matched the
previous run's shape to the posting. The *bytes* are not deterministic —
posting and transaction IDs are UUIDv7 and `created_at` is stamped from the
wall clock. Compare fixtures by shape, never by hash.

## Fixtures

| T0 | 24 | 200 | 4,800 | 9,600 | 3,848 | 3.8 s |
| T1 | 120 | 200 | 24,000 | 48,000 | 19,181 | 19.7 s |

All tiers: 20 deposit accounts (102 accounts total), 80 categories, 0.80

fixture mtimes and exclude the `cargo build --release` step.

**T0→T1 lengthens history at constant transaction density (24→120 months,
same 200 tx/month); T1→T2 holds history constant and multiplies density 10×
(200→2000 tx/month).** These are two different axes of scale, and the tier
steps are *not* the same size — any argument comparing a T0→T1 growth factor
against a T1→T2 growth factor must normalise first.

### The dominant account

The generator's `--skew` knob concentrates **~30% of transactions** on one
deposit account. Because each transaction has two legs and only one lands on
a deposit account, that is **~15% of postings**, not 30%. Measured on these
fixtures:

| Tier | Dominant-account postings | Share of all postings | Share of transactions |
| ---- | ------------------------- | --------------------- | --------------------- |
| T0 | 1,413 | 14.7% | 29.4% |
| T1 | 7,248 | 15.1% | 30.2% |
| T2 | 72,117 | 15.0% | 30.1% |

Dominant-account posting counts grow **5.13×** (T0→T1) then **9.95×**
(T1→T2) — the asymmetry that makes raw growth-factor comparisons invalid.

`balance_for`, `account_period_stats`, and `posting_buckets` all target this
account. They are a realistic worst case for one busy account, not a typical
account. `default_balances` and `net_worth` sum every account and are the
whole-ledger figures.

## Interpretation

### 1. `posting_buckets` cost tracks *total* history, not window size

`posting_buckets` requests a fixed, bounded **6-month window** on the dominant
account. At T1 and T2 that window holds roughly 5% of the account's postings.
If cost were a function of the window, T0 ≈ T1 would be expected and only
T1→T2 (10× density inside the window) would matter.

That is not what happens. Normalised per **dominant-account posting** — the
account's *total* posting count, ignoring the window entirely:

| Tier | Dominant postings | `posting_buckets` | Cost per total posting |
| ---- | ----------------- | ----------------- | ---------------------- |
| T0 | 1,413 | 19.456 ms | 13.8 µs |
| T1 | 7,248 | 148.70 ms | 20.5 µs |
| T2 | 72,117 | 1.7728 s | 24.6 µs |

A bounded 6-month window costs **in direct proportion to the account's total
posting count**, across a 51× span of that count and across both scaling axes.
That is exactly what an unbounded residual load predicts, and it is not
explicable by window size. Time grows 7.64× and 11.92× against count growth of
5.13× and 9.95× — close to proportional, with a mild upward drift in the
per-row constant.

Note honestly what this is *not*: there is no dramatic superlinearity. The
per-row constant rises modestly (13.8 → 20.5 → 24.6 µs), and T0's lower
constant is **unexplained** — plausibly cache residency at 6 MB of database,
but nothing here measures that, so it is left open. The load-bearing
observation is the proportionality to total count, not the drift.

**Mechanism, confirmed by reading the code.**
`fetch_postings_in_range` date-scopes its own SQL, but whenever any elided leg
falls in-window it calls `Residuals::for_account` with **no date bound** at
`crates/bc-core/src/balance.rs:293`. `crates/bc-core/src/residual.rs:159-168`
then selects every leg of every transaction owning an elided posting on that
account, **over all time**. With an 0.80 elided ratio, essentially every
window hits this path.

`account_period_stats` additionally performs an *unbounded* `genesis..from`
opening-balance load **by design**, so it scales with total history regardless
of window: 47.782 ms → 329.83 ms → 3.4721 s (6.90× then 10.53×).

### 2. Hardware and variance

All numbers come from a single run on one machine. Criterion's bracket
reflects real sample variance, and some T1 brackets are wide (e.g.
`default_balances/t1`: 544–703 ms). Treat every figure as an estimate with its
stated bracket. Expect different absolute numbers — though probably similar
ratios — on other hardware.

## Query plans

Verified with `EXPLAIN QUERY PLAN` against the regenerated T1 fixture,
read-only, using bound parameters rather than inlined literals (SQLite's plan
for `?1 IS NULL OR …` depends on it). Two defects, both wider than the issues
as filed.

**(a) The "date-bounded" queries are unbounded in execution.** Both queries in
`fetch_postings_in_range` put the `t.date` predicate on the *joined* table, so
it cannot restrict the driving index scan:

```text
-- concrete legs
|--SEARCH p USING INDEX idx_postings_account_commodity (account_id=? AND commodity=?)
`--SEARCH t USING INDEX sqlite_autoindex_transactions_1 (id=?)

-- elided legs
|--SEARCH p USING INDEX idx_postings_account (account_id=?)
`--SEARCH t USING INDEX sqlite_autoindex_transactions_1 (id=?)
```

SQLite walks **all** of the account's postings, probes `transactions` by
primary key once per row, and applies the date test post-join. A 6-month
window and a 10-year window drive the same number of index steps.

**(b) `Residuals::load` full-scans the whole `postings` table on every call,
for every account.** The `(?1 IS NULL OR e.account_id = ?1)` disjunction at
`residual.rs:165` is not sargable, so `idx_postings_account` is unusable:

```text
|--SEARCH sib USING INDEX idx_postings_transaction (transaction_id=?)
|--LIST SUBQUERY 1
|  `--SCAN e                                    <-- full table scan
`--USE TEMP B-TREE FOR LAST TERM OF ORDER BY
```

Splitting the disjunction into two query strings restores the index — verified
by running the split form against the same fixture:

```text
|  `--SEARCH e USING INDEX idx_postings_account (account_id=?)
```

This is a sargability bug **independent of date scoping**: even a small account
pays whole-ledger cost on every residual load. #370 as filed understates the
problem.

**Consequence for the planned fix.** The design settled on scoping only the
*inner* elided subquery of `Residuals::load` by `t.date`. That is necessary but
**not sufficient**: it leaves both defects above untouched, so implementing it
as written would barely move `posting_buckets`. A complete fix needs all three
— scope the inner subquery, make the account predicate sargable, and restructure
`fetch_postings_in_range` so its date bound can actually drive the scan.

## Verdicts

Criteria were fixed in advance, before any measurement, and are restated here
in full so this document stands alone.

### #370 — date-scope the residual query

> Justified if `account_period_stats` on the dominant account exceeds ~50 ms at
> T1, or scales worse than linearly.

**Measured: 329.83 ms at T1, ~6.6× the 50 ms threshold → JUSTIFIED.**

Corroborated by the mechanism above: a bounded window provably costs in
proportion to unbounded history. But see *Query plans* — the fix as scoped is
partial, and the sargability defect is a second, independent bug.

### #362 — set-based `net_worth` and `report`

> Justified if `net_worth` at T1 exceeds ~100 ms, **or** exceeds
> `default_balances` by more than ~2× — the latter proving the N+1 is the
> dominant term rather than the postings scan.

**Measured: `net_worth` at T1 = 465.55 ms, ~4.7× the 100 ms threshold →
JUSTIFIED** on the first branch.

**The second branch — the discriminator — came back decisively negative, and
its pre-registered inference must be drawn.** `net_worth` / `default_balances`
is **0.74×** at T1 (465.55 vs 624.90 ms); 1.02× at T0 and 0.83× at T2.
`net_worth` is *faster* than the set-based pass at every tier, nowhere near
the 2× that would indict the N+1.

**Inference: the N+1 is not the dominant term. The postings scan is.**

The consequence is important and cuts against the issue's framing: rewriting
`net_worth` to be set-based would make it **the same speed or slower**, because
it becomes `default_balances` plus a sibling query for the requested commodity
(`default_balances` returns each account's *default* commodity, which
`net_worth` cannot use directly). #362 remains worth doing for **correctness
and code shape** — one code path instead of two, no per-account residual
re-resolution — but **this data does not support a performance win, and the
issue should not claim one.**

### #244 — populate the balances cache

> Justified only if `default_balances` — the already-set-based floor — itself
> exceeds ~100 ms at T1.

**Measured: `default_balances` at T1 = 624.90 ms, ~6.2× the 100 ms threshold →
JUSTIFIED as written.**

**But the criterion's own premise does not survive the measurement, and saying
so is the point of the exercise.** The criterion calls `default_balances` a
*floor*. It is not. Cost per posting:

| Tier | Postings | `default_balances` | Cost per posting |
| ---- | -------- | ------------------ | ---------------- |
| T0 | 9,600 | 97.685 ms | 10.2 µs |
| T1 | 48,000 | 624.90 ms | 13.0 µs |
| T2 | 480,000 | 6.4640 s | 13.5 µs |

**13.0 µs per posting at T1** is one to two orders of magnitude above what a
decode-parse-add loop costs. The pass is not near any hardware floor; it is
paying an unoptimised constant — sqlx row decode, a `String` allocation per
amount, a `Decimal` parse, and `HashMap` churn. A ~6.2× constant-factor win in
the *existing* pass puts T1 under the 100 ms bar with no cache and no
invalidation surface at all.

So the honest statement is narrower than the verdict suggests:

> **Today's set-based implementation is too slow at T1.** That is *not* the
> same as "no set-based implementation can meet the budget," and the
> measurement cannot distinguish the two.

This admits **two** remedies, and only the second was priced this cycle:

1. **Optimise the existing pass** — borrowed decode, arena/interned commodity
   codes, avoiding the intermediate `String`, pre-sized maps. No invalidation
   surface, no new correctness obligations. Unpriced.
1. **Build the cache** (#244) — `O(accounts)` reads, at the cost of
   write-through maintenance, an invalidation unit of the *transaction* (an
   elided leg depends on its siblings), and a `verify`/repair command.

**Remedy 1 should be attempted and measured before remedy 2 is committed to.**

### Does #244 resolve #370 and #362?

The original framing assumed it does. It does not, for two reasons independent
of any measurement.

**The `balances` table cannot answer the opening-balance query.** As it exists
in the schema today it is `PRIMARY KEY (account_id, commodity)` with columns
`(amount, updated_at)` — a *current* balance with **no date axis** — and it is
present but **never populated** (0 rows in every fixture). `account_period_stats`
needs `posting_flows(account, commodity, Date::MIN, from)`, a prefix sum from
genesis to an arbitrary date. A current-balance row cannot serve that, nor the
time-travel queries the design contemplates. **#370's opening-balance load
survives the cache entirely** — which is also why #370's own payoff is capped:
date-scoping fixes two of `account_period_stats`'s three residual loads, and the
third is unbounded by construction. If a cache is built, its shape must be
decided on this basis, not inherited from the existing DDL.

**There is no rebuild path from the event log, and one cannot be built today.**
#244's acceptance criteria call for a rebuild from the event log, but the log is
lossy *by design*: `TransactionAmended` does not capture posting or tag
mutations, `AccountUpdated` carries only an id, `loan_terms` cannot be recovered
by replay ("the projection DB is canonical"), and `ImportBatchDiscarded` is
deliberately excluded from replay. The rebuild source must therefore be the
**postings table** — i.e. `default_balances` itself, which conveniently doubles
as the divergence oracle. **#244's acceptance criteria need correcting on this
point**, otherwise they imply a far larger event-log project than intended.

### Summary

All three issues clear their pre-registered thresholds at T1 by 4.7–6.6×, well
outside criterion's variance brackets. No verdict turned on a close call.

But two of the three need their *rationale* corrected:

- **#362** is justified for correctness and code shape, **not** for
  performance — its own discriminator ruled the N+1 out as the dominant term.
- **#244** is justified against *today's* implementation only. The cheaper
  remedy (optimise the existing pass) was never priced, and the cache does not
  resolve #370 or #362 regardless.
